# ANN（ann1678.com）

相場を予測して、仮想で売買し、その記録をすべて公開するサイト。
本番は **https://ann1678.com/** で動いている。

**予測は結果が出る前にコミットする。** このリポジトリの履歴が、後から書き換えていないことの証明になる。
だから公開リポジトリにしてある。

---

## 何が動いているか

```
Xserver（毎時5分の cron: ~/ops/dispatch.sh）
  0. GitHub に「エンジンを回せ」と合図を出す ← **時刻を守るのはここ**
        ↓
GitHub Actions（合図で動く。予定実行は保険で毎時5分 UTC に置いてある）
  1. engine/run.py      相場を取る → 判定 → 手仕舞い → 予測 → 集計
  2. data/ をコミット   ← ここが証拠。追記だけで、書き換えない
  3. サイトを組む       Astro でビルド
  4. deploy ブランチへ置き換える（履歴は毎回捨てる。1コミットだけ）
        ↓
Xserver（5分ごとの cron: ~/site-pull.sh）
  5. deploy ブランチを取りに行き、~/ann1678.com/public_html へ反映する
```

**GitHubにサーバーの鍵を預けていない。** サーバーが公開リポジトリを取りに行くだけなので、
本番の鍵はどこにも置いていない。

**⚠ 逆向きに鍵が1本ある。** GitHub のトークンを Xserver の `~/.config/quant-live/github-token` に置いている。
できるのは「このリポジトリのワークフローを動かす」ことだけで、コードは読めず push もできない。
漏れてもエンジンを余計に回されるだけで、記録は二重にならない（予測は `pid`、手仕舞いは `seg_id` で弾く）。
入れ方と作り方は `ops/dispatch.sh` の頭に書いてある。

**⚠ GitHub の予定実行（schedule）は来ない。** 2026-09-12の実測で 80.3時間に22回、27%だった。
分を動かしても変わらない（:05 で28%、:37 で27%）。これが原因で 2026-09-11 に手仕舞いが4時間半おくれ、
公開していた売買2件の符号が両方とも裏返った。だから合図はサーバーから出す。

| 何 | どこ |
|---|---|
| 予測エンジン | `engine/`（Python・requests だけ）。`strategy.py` 予測／`paper.py` 約定の前提／`sim.py` 過去への当てはめ／`stats.py` 数え方／`report.py` 集計と関門 |
| 研究 | `research/`（numpy・pandas。エンジンには使わない）。検証台・候補6本・設計の記録・監査のメモ |

| 手記 | `content/posts/`（Sveltia CMS で書く。入口は `/admin/`） |
| 記録 | `data/`（**Actions が書く。手で触らない**） |
| サーバー設定 | `deploy/htaccess`（旧URLの転送もここ） |

## 記録の決まり（崩すと、このサイトの意味が消える）

1. **`data/*.jsonl` は追記だけ。** 予測・結果・売買を後から書き換えない
2. **予測は結果より先に書く。** `run.py` は判定してから予測する順番で組んである
3. **バックテストと事前公開の記録を混ぜない。** `backtest.json` は別ファイルで、ページでも別の場所に出す
4. **モデルを変えたら `strategy.py` の `MODEL` の名前も変える。売買の規則を変えたら `paper.py` の `RULE` も変える。** 変えないと違うやり方の成績が同じ欄に混ざる。集計は `MODEL` と `RULE` で分けている
5. **パラメータを後から成績のいい値へ寄せない。** 寄せた時点で、その成績は過去への当てはめになる
6. **関門は決めた件数のときだけ検査する。** 銘柄ごとに 50・100・200・400 件で t ≥ 2.36。毎時見て最初に越えた瞬間を合格にすると、優位が無くても3〜4割で合格が出る。結果は `data/gate.jsonl` に追記する

## いま分かっていること

### v1（ema-cross-v1）には優位が無かった（2026-09-09）

90日の当てはめは BTC +0.22%／ETH +0.32% だった。**4年（2022-09〜2026-09）・6銘柄に当てると平均はマイナスになる。**
毎時の的中率は 47〜50% で、ランダムと変わらない。90日のプラスは 2026-08-18→08-21 の1件が作っていた。
起点をずらすと符号が変わる。72通りのうち BTC は 35通りでマイナス（中央値 +0.03%）。1本では変わらないが、9本ずらすと −0.21% になる。
詳細は `research/README.md` と `research/design/baseline.md`（4年の数字）。

### v2（tsmom-vote-v2 ＋ long-carry-v2）は「事前に登録した仮説」で、優位は証明されていない

| | 予測 | 売買の規則 |
|---|---|---|
| v1 | 1時間足 EMA12/48 のクロス。ATR×0.15 で見送り | 上も下も建てる。72時間で必ず閉じる。建て値は閉じた足の終値 |
| v2 | 7・14・28日リターンの符号の多数決 | **上だけ建てる。**72時間後に同じ向きなら持ち越す（区間ごとに1件で記録）。建て値は run 時点の気配。手数料は銘柄ごと（BTC 0.10%・ETH 0.12%）＋すべり 0.05%。ショートには建玉管理料 0.04%/日 |
| v3 | v2 と同じ（モデルは変えていない） | **売買の規則だけ変えた。**建て値は合図にした足の終値、手仕舞い値は期限の足の終値。**run した時刻に左右されない。**実際に板にあった値は `entry_actual` / `exit_actual` に、期限からの遅れは `late_minutes` に残す |

**⚠ 2026-09-12に `long-carry-v2` から `long-carry-v3` へ改めた。**
v2 は「run した瞬間の気配」で約定したことにしていて、記録が実行の時刻に左右された。
2026-09-11に4時間半おくれ、閉じた2件の符号が両方とも裏返った（btc −0.198% は本来 +1.690%、eth −5.103% は本来 +0.391%）。
**v1 で足をやめたのは足が悪かったからではなく、毎時37分で40〜70分おくれていたからだった。**直すのは規則ではなく時刻のほうで、
足に戻したうえで合図を毎時5分に寄せた。v2 までの2件は書き換えず、`/record/` の下に分けて残してある。

4年の1時間足を訓練（2022-09〜2025-03）・検証（2025-03〜2026-03）・試験（2026-03〜2026-09、1回だけ）に分けて、
6つの角度（日次モメンタム・約定・銘柄横断・暦・ブレイクアウト・反転）で候補を作り、審査した。
**どの候補も、検証期間でプラスの優位を偶然と区別できなかった。**v2 はその中でいちばん筋の通った仮説を、証明抜きで置いたもの。

| v2（区間＝72h、BTC+ETH） | 件数 | 1件あたり平均 | t | 常時ロング |
|---|---|---|---|---|
| 訓練 | 415 | +0.53% | 2.1 | +0.43%（t 2.2） |
| 検証 | 147 | +0.45% | 1.0 | +0.07%（t 0.2） |
| 試験（1回だけ） | 90 | +0.57% | 1.3 | +0.43%（t 1.0） |

この表の BTC は手数料 0.12% で計算している（engine は API の値 0.10%。差は1件あたり 0.04pt）。
**優位があれば本番の記録で出る、とは言い切れない。**1件 +0.5%・ばらつき 5% の優位でも、400件で見つかる確率は4割ほど（検出力）。
無ければ 400 件で終わる。それを決めるのが関門（下）。いまの建て方だと1銘柄 400 件に約6年かかる（年 65〜70 区間）。

### 関門（report.py）

銘柄ごとに、閉じた区間の net% の t ＝ 平均 ÷ 標準偏差 × √件数 を、**件数が 50・100・200・400 に達したときの4回だけ**検査する。
t ≥ 2.36 で合格（4回で偽陽性は銘柄ごとに約3%。どちらかの銘柄が通る確率は約5%）。400件で合格しなければ、このモデルは終わり。
合否は丸める前の t で決め、`gate.jsonl` には3桁に丸めた t を書く。
v1 の関門「毎時 (1.96×sd/mean)² と比べる」は、優位が無くても 30〜40% で合格が出る設計だった（`research/design/` の監査）。

### 手数料の事実（bitbank API `/v1/spot/pairs`、2026-09-09）

btc_jpy テイカー 0.10%（メイカー 0）／eth_jpy テイカー 0.12%（メイカー −0.02%）／信用取引の建玉管理料 0.04%/日（JST 0:00 の建玉）。
現物ではショートできない。

## 見た目

デザインの正本は `src/styles/global.css`。お手本は **block.xyz**（2026-09-10に実測）。
書体は Inter（英数）と Zen Kaku Gothic New（かな漢字）の2つだけ。等幅はモデル名と式にだけ使い、Webフォントは読み込まない。

⚠ **見出しの太さを900に戻さない。** 極太の見出しと、罫で囲んだ数字の格子が、前の作りが野暮ったく見えた原因。
見出しは500、数字も500、節は罫ではなく空き（`--gap`）で区切る。数字の上にだけ細い罫を1本ひく。

### 色（2026-09-12にデジタル寄りへ入れ替えた）

| 変数 | 値 | 仕事 |
|---|---|---|
| `--up` | `#0055ff` | 上・プラス。字にも面にも使える |
| `--down` | `#c9410a` | 下・マイナス。**字と線だけ** |
| `--down-lit` | `#ff5a1f` | 下。**塗りの面だけ。**この上には墨の字を置く |
| `--live` / `--live-lit` | `#00b4d8` / `#2fe0ff` | 動いていること。点・走査線・黒地の左の線 |

⚠ **`--down` と `--down-lit` を入れ替えない。** 紙の上で明るい橙は対比が3.0しか出ず、字にすると読めなくなる。
⚠ **シアンを字に使わない。** 紙の上では2.4しか出ない。黒地の上と、地の色と、線だけ。
⚠ 緑と赤は使わない。日本の板は上げが赤・米国は上げが緑で、逆に読まれる。青と橙なら取り違えようがなく、赤緑の色覚でも分かれる。

### 計器の層（2026-09-12に足した）

block.xyz の色と字はそのままに、**機械が動いていることを見せる層**を重ねた。

| 何 | どこ | 中身 |
|---|---|---|
| 頭の黒帯 | `.statusbar`（`Base.astro`） | 稼働中の点滅・モデル名・規則名・最終更新・日本時間の秒。値は `summary.json` から取る |
| 走査線 | `header.site::after` | 頭の下の罫を、青い光が6.5秒かけて左から右へ渡る |
| 等幅の小札 | `.eyebrow` `thead th` `td.ts` `.rows time` | かな漢字は `--mono` の末尾に置いた Zen Kaku へ落とす。書体は2つのまま |
| 目盛り | `.stat::before` `.panel::before` | 数字の上の罫の左端から、6〜9px の爪を下ろす |
| 粒の棒 | `.progress` | 進み具合を塗りつぶさず、3px おきの粒に割る |
| 秒で動く数字 | `.v.tv`（`index.astro` のヒーロー） | 最終更新からの経過と、次の判定までの残り。`data-from` と `data-until` に時刻を置くと、`Base.astro` の1本の `setInterval` が拾う |
| 関門の目盛り | `GateScale.astro` | 0件から400件までの線に、検査する4点を打つ。次の1点だけ青にする |
| 向きの3枠 | `Votes.astro` | 7・14・28日の向きを3つの枠で出す。上は青を上へ、下は橙を下へ寄せるので、色が見分けられなくても読める |
| 資金の推移 | `Equity.astro` | 元手を破線で引いて、そこからの上下を描く。**点が5つ未満のときは出さない**（`index.astro` で見ている）|
| 反転した式 | `.formula` `.prose pre` | 地を `#0d0d0f` にして、左に青い線を1本ひく |

⚠ **地に縦の罫を敷かない。** 2026-09-12に88pxの方眼を試して、CEOの指示で外した。
⚠ **黒帯を28pxより厚くしない。** ここが厚いと、お手本の余白が効かなくなる。
⚠ **ゼロの斜線（`zero`）は Google Fonts の Inter に入っていない。** 書いても出ない（2026-09-12 実測）。

動きは4つ（点滅・走査線・秒で動く数字・押したときの色）だけで、`prefers-reduced-motion` で色と走査線が止まる。
秒の数字は時刻そのものなので止めない。**`setInterval` はページ全体で1本だけにする。**要素ごとに立てると、数字が増えるほど重くなる。
