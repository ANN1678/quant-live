# tsmom — 日次スケールの時系列モメンタム（検討の記録）

結論を先に書きます。**この角度では、手数料を引いた後の1回あたりの損益を偶然と区別できる形にはなりませんでした。**
train で 15 通り試し、valid は 2 回だけ見ました。事前に決めた主案の valid は pooled で平均 +0.79%、t=+0.52 です。プラスですが、必要件数は 1256 件で、1件が 500 時間かかる売買では届きません。

## 0. 先に決めたこと（train の数字を見る前に書いた）

根拠にした文献
- Moskowitz, Ooi, Pedersen (2012) "Time Series Momentum": 過去リターンの符号で方向、事前ボラで大きさを調整（目標 40%/年）
- Liu, Tsyvinski (2021) "Risks and Returns of Cryptocurrency": BTC/ETH/XRP は 1〜4 週の過去リターンが翌週を予測する（日次データでは 1〜7 日）
- Harvey ほか (2018) "The Impact of Volatility Targeting": 実現ボラの逆数で大きさを調整すると、リスク資産の Sharpe が上がり、深い下落が浅くなる

信号（毎時、閉じた1時間足だけで計算）
- r_N = c[i] / c[i − 24N] − 1、N ∈ {7, 14, 28}（1週・2週・4週）
- 主案: 3つの符号の多数決（sign(Σ sign(r_N))）。ゼロ割れは 0
- 副案: 3つが一致したときだけ建て、割れたら見送り
- 大きさ: size = min(1.0, 目標ボラ ÷ 実現ボラ)。実現ボラ = 直近 20 本の「重ならない 24 時間リターン」の標本標準偏差、目標 = 2.0%/日（MOP の 40%/年に近い）
  ※ harness の per-trade net_pct には size は効かない（資金曲線と最大DDにだけ効く）。見送りには使わない

保有と約定
- 主案: H = 168（Liu–Tsyvinski の週次リバランスに合わせる）、hold_through=True（符号が同じなら建て直さずに延ばす＝MOP の月次リバランスと同じ考え）
- 比較: H ∈ {72, 120}、hold_through=False
- fill = next_open、コスト = DEFAULT_COSTS（テイカー 0.12% + すべり 0.05% 片道、ショートは建玉管理料 0.04%/日）

試す順番（変種の数を絞るため）
1. H=168, hold_through=True を固定して、信号 5 種（多数決／一致／単独 7／単独 14／単独 28）を train・5 銘柄で比べる
2. 選んだ信号で H と hold_through を動かす（3×2）
3. valid は最後に 1 つ（多くて 2 つ）だけ

必要な助走: 28 日 = 672 本 + 1。harness の既定の warmup（720 本）に収まる

## 3. 診断: 符号に予測力があるか（train、コスト前）

コスト前で情報比 0.05 なら必要件数は約 1500 件で、往復 0.34% を引けばさらに遠のきます。**この時点で、この角度の中でパラメータを動かしても届かないと判断し、探索を止めました。**

## 6. 運だけの基準線との比較

`snooping_baseline(50)`（btc+eth、H=168）: ランダム 50 個の train 最良は hold_through=True で t=+1.70（その valid は −3.03）、False で t=+1.38（valid −3.59）。
主案 A の train t（btc+eth）は +0.12 で、運だけの最良より低いです。A は train で選んだものではないので直接の比較にはなりませんが、train の数字に意味がないことは分かります。valid では A の +1.03 が運の最良の −3.03 を上回ります。ただし n=38 です。

## 7. 変種の数（正直な数え方）

- evaluate に通した戦略の設定: **15 通り**（step 1 が 5、step 2 が 10）。final の B は step 2 の 1 つと同じ設定です
- 診断の走査: (N, H) の 36 組 × 5 銘柄。戦略の選択には使っていません
- valid を見た回数: **2 回**（A と B）。年ごとの y3/y4 は valid と重なるので、A と B の 2 つだけで回しました
- test は触っていません

## 8. 選んだ理由と、選ばなかった理由

候補ファイルは事前に決めた主案 A のままにしました。train の t が最も高かったのは単独 28（+1.04）ですが、0.13 の差は 15 通りの中の並び順で決めるべき差ではありません。
hold_through=True を残したのは、それが文献どおりの TSMOM の形だからです。サイトの関門に合わせるなら B（固定 H）のほうが実装は簡単で、数字は §5 に出してあります。どちらも関門には届きません。

## 9. 実装の要点（本番に載せる場合）

- 必要な足: 閉じた 1 時間足 673 本（28 日 + 1）。ボラは 481 本。run.py の `market.candles(pair, "1hour", days=10)` を days=29 以上にします（1 日 1 リクエスト、0.1〜0.25 秒なので 1 銘柄 6 秒程度）。NOTES.md の UTC 日付の不具合も同時に直す必要があります
- 計算: c[-1]/c[-1-24N] − 1 を 3 つ、符号の和の符号、24 時間おきに取った 20 本のリターンの標本標準偏差。純 Python で 30 行、1 時間あたりの計算量は定数です
- hold_through: run.py の手仕舞い（3）で、期限が来た玉の方向と当日の信号が同じなら期限を 168 時間延ばす、という分岐が要ります。paper.py と trades.jsonl の「1 件」の意味が変わるので、B（固定 H）のほうが載せやすいです
- size: paper.py の POSITION に size を掛ける口が要ります。いまは固定 10% です
- 予測の判定は 168 時間先なので、サイトの毎時の的中率は 168 本重なります。実効件数は判定数の 1/168 程度です

## 10. 危険

- 優位そのものが無い。コスト前の情報比 0.03〜0.05 は、4 年で見ても偶然と区別できない
- pooled のプラスは DOGE と XRP の 2024 年秋〜2025 年春の上げ（y3）が作っている。y1 と y4 はマイナス
- 勝率 3 割で 1 件の sd が 14〜32%。サイトに出すと「負け続けてたまに大勝ち」に見える
- ショートは 1 件で 0:00 JST を 20 回前後またぎ、建玉管理料だけで 0.8% 前後かかる
- 1 件が 500 時間なので、valid 1 年で btc+eth 合わせて 38 件しか閉じない。関門の判定に必要な件数は年単位では集まらない
